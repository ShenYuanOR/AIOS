# AIOS 系统架构与设计文档

本文档对 AIOS（工位 OS）的母子分级机制、死核架构、工作间隔离与插件体系进行系统性梳理。

---

## 一、架构总览与核心设计理念

AIOS 是基于 **NixOS 原生系统 + 定制命令（加法）+ 签名热插拔插件 + 隔离 MicroVM 工作间** 构建的工位 AI 操作系统。

```text
┌───────────────────────────────────────────────────────────────┐
│                        用户（哥哥）                           │
└──────────────┬───────────────────────────────┬────────────────┘
               │ TTY 全屏 / SSH                │ 直达 Slash
               ▼                               ▼
┌──────────────────────────────┐ ┌──────────────────────────────┐
│  母（Mother / 全能操作员）   │ │   核 Slash（不经大模型）     │
│  - 居住在 aios 家里（宿主）  │ │   - /status, /help, /spawn   │
│  - 账本工作集与自然语言注入  │ │   - /attach, /idle, /reap    │
│  - 需求分析与任务拆解        │ └──────────────┬───────────────┘
└──────────────┬───────────────┘                │
               ▼                                │
┌───────────────────────────────────────────────▼───────────────┐
│                      motherd（系统死核）                      │
│  - 纯 Rust 实现，不扩 syscall，纯粹的调度与控制中枢           │
│  - 系统调用：spawn · attach · reap · cap_call · audit ...     │
│  - 哑柜（Vault）凭证隔离 · 插件验签中枢 · 资源配额管控       │
└──────────────┬────────────────────────────────┬───────────────┘
               │ 签名热插拔                     │ 按需落实开房
               ▼                                ▼
┌──────────────────────────────┐ ┌──────────────────────────────┐
│       Plugins 插件生态       │ │   工作间（MicroVM 房间）     │
│  - mother-nl (自然语言中枢)  │ │   - 落实复杂/排异实验        │
│  - model-router (多模路由)   │ │   - 子（Child）租客常驻      │
│  - mux-skill, cockpit-web    │ │   - 独立 SSH:2222 接入       │
│  - metrics-export, archive   │ │   - 房内 CLI 与宿主母解耦    │
└──────────────────────────────┘ └──────────────────────────────┘
```

### 核心三原则
1. **脑与工位解耦**：模型是大脑，母是全能用户代理。大模型即便宕机或断网，工位与底层 NixOS 系统原生命令完好无损。
2. **就近处理原则**：家里能办的在家里办；只有工具不在家里或需要危险/排异实验时，才按需 `spawn` 工作间。
3. **核与插件分立**：死核 `motherd` 严格收敛，绝不私自扩张 syscall；所有的业务逻辑、大模型交互、工具调用均作为插件热插拔进化。

## 二、母（Mother）与子（Child）运行机制

### 1. 母（Mother / 家里）
- **定位**：常驻在宿主系统的全能用户代理，交互形态为 TTY 全屏界面（基于 ratatui + crossterm），用户登录 `aios` 用户即进入「家里」。
- **职责**：
  - 倾听哥哥的意图，管理会话账本与上下文工作集。
  - 将高级意愿转化为已登记的系统动作或核 Slash 命令。
  - 在宿主环境直接执行安全的原生 PATH 命令（`cap_call host.run`）。

### 2. 工作间（MicroVM / 房间）与子（Child）
- **定位**：轻量级虚拟化隔离环境，按需通过 `spawn` 创建，用于隔离依赖冲突、重度构建或具有安全风险的代码实验。
- **职责**：
  - 拥有独立的根文件系统和网络命名空间。
  - 租客（子）在工作间内进行操作，通过独立端口（如 `ssh -p 2222 root@...`）供外部接入。
  - 房内 CLI 与母对话 CLI 完全解耦，工作间生命周期受死核严格监控（`idle` / `reap` / `archive`）。

## 三、死核系统调用（Syscalls）与 Slash 指令

### 1. 系统调用表（Syscall）
| 调用名 | 核心功能 | 访问约束 |
|---|---|---|
| `spawn` | 启动并初始化一个新的工作间 MicroVM | 由母代交或 Slash 直达 |
| `attach` | 将控制台/终端接入指定工作间 | 提供接入指针与状态校验 |
| `reap` | 销毁已完成任务的工作间并回收资源 | 释放 CPU/内存/磁盘配额 |
| `cap_call` | 跨安全边界能力调用（如 `host.run` 执行宿主命令） | 白名单机制，aios 权限执行 |
| `audit` | 记录全生命周期的系统审计与操作日志 | 只追加，不可篡改 |
| `secret_get` | 从安全哑柜（Vault）提取受保护凭证 | 仅限已验签插件受控获取 |
| `quota` | 检查并核算当前资源用量与调用配额 | `/help` 依赖此通道拉取状态 |
| `bootstrap` | 系统启动引导与基础环境拉起 | 系统初始化专用 |
| `rescue` | 故障隔离与安全救援模式 | 紧急恢复通道 |

### 2. Slash 指令集（人手直达，不经模型）
- `/status`：显示当前宿主负载、内存、母状态与活跃工作间。
- `/spawn`：手动创建并拉起新工作间。
- `/attach`：手动附加到目标工作间。
- `/idle`：将工作间置为闲置休眠状态。
- `/reap`：手动清理指定工作间。
- `/archive`：归档工作间产物并冻结环境。
- `/help`：拉取核与已签名插件注册的所有命令一览。

## 四、插件验签与安全隔离

1. **Manifest 规范**：每个插件根目录必须包含 `manifest.toml`，在 `[[commands]]` 中明确声明其提供的命令与能力。
2. **签名闭包**：生产环境中插件必须附带 Ed25519 签名闭包，死核加载时校验私钥签名。未通过验签的插件视同不存在。
3. **哑柜（Vault）凭证管理**：API 密钥（如 `model.*.api_key`）与私有证书统一落入死核管理的哑柜中，插件在运行时动态申请，内存使用，绝不落盘，绝不进 Git。
