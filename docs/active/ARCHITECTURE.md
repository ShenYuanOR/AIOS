# 系统架构与运行机制 (System Architecture)

本文档以客观、中立的工程视角阐述 AIOS 的系统边界、控制面/执行面分离架构、状态机流转与安全边界。

---

## 1. 架构分层与职责边界

系统划分为三个明确解耦的层级：

```text
┌─────────────────────────────────────────────────────────────┐
│ 交互与呈现层 (Presentation Layer)                          │
│ - TTY Client (motherctl): 基于 ratatui/crossterm 的终端前端 │
│ - 标准 SSH 接入点 (Port 22 / Port 2222)                     │
└──────────────────────────────┬──────────────────────────────┘
                               │ IPC / Unix Domain Socket
┌──────────────────────────────▼──────────────────────────────┐
│ 控制面死核 (Control Plane: motherd)                         │
│ - 状态机调度、MicroVM 生命周期管理 (microvm.rs, lease.rs)   │
│ - Syscall 路由器、资源配额检查 (syscall.rs, audit.rs)       │
│ - 哑柜凭证安全管理 (vault.rs)、插件签名验签器 (loader.rs)    │
└──────────────┬──────────────────────────────┬───────────────┘
               │ 进程/管道隔离                │ KVM / VirtIO 隔离
┌──────────────▼──────────────┐ ┌─────────────▼───────────────┐
│ 扩展插件面 (Plugins Layer)  │ │ 隔离执行环境 (Workspace)    │
│ - mother-nl (NLP意图分发)   │ │ - MicroVM 独立内核与Rootfs  │
│ - model-router (多端路由)   │ │ - 独立网络命名空间与端口     │
│ - 外部工具/指标监控插件     │ │ - 承载构建与非信任代码执行  │
└─────────────────────────────┘ └─────────────────────────────┘
```

### 1.1 控制面与大模型解耦 (Decoupling)
- **不变控制面**：`motherd` 采用 Rust 原生实现，不依赖 Python 运行时或大模型在线服务。大模型仅作为自然语言解析器（NLP Coprocessor），无权直接调用底层系统调用。
- **失效隔离**：当上游模型 API 发生网络超时、限流或返回异常结构时，`motherd` 状态机维持运行，Slash 命令（`/status`、`/reap` 等）及底层 NixOS 原生命令保持 100% 可用。

### 1.2 宿主环境（家里）与虚拟化工作间（工作间）
- **宿主执行域**：
  - 用户登录默认进入 `aios` 宿主域。
  - 常规命令通过 `cap_call host.run` 在宿主执行（以 `aios` 普通用户权限派生进程，非 PTY 模式，限制标准输入输出捕获上限为 256KiB）。
- **工作间隔离域**：
  - 触发条件：环境需要污染性依赖、存在内核参数破坏风险或需要独立多端口网络服务时，显式派生 MicroVM。
  - 访问路径：工作间通过宿主 TAP 网络分配独立 IP，或通过转发端口（如 `ssh -p 2222 root@<LAN_IP>`）直连。
  - 生命周期：由 `motherd` 分配租期（Lease），支持 `active` -> `idle` -> `reap` / `archive` 状态流转。

## 2. 核心系统调用与指令分流逻辑

### 2.1 系统调用 (Syscalls)
死核仅暴露收敛的基础系统调用，禁止插件动态追加 syscall：
1. `spawn(template, quota)` -> 创建 MicroVM 实例并返回唯一实例句柄。
2. `attach(instance_id)` -> 校验实例状态并返回终端接入参数。
3. `reap(instance_id)` -> 终止 QEMU/MicroVM 进程，释放 TAP 网卡与配额。
4. `cap_call(cap_name, payload)` -> 经由审计拦截的能力调用（如宿主命令执行）。
5. `audit(event)` -> 追加写入结构化审计日志。
6. `secret_get(key)` -> 从 Vault 内存结构提取解密凭证，拒绝未验签插件访问。
7. `quota(scope)` -> 查询系统与租户的 CPU、内存、存储与并发限制。
8. `bootstrap()` / `rescue()` -> 系统自检与紧急恢复通道。

### 2.2 命令分流流程 (Command Dispatch Pipeline)

```text
用户输入
   │
   ├─[以 '/' 开头] ──> 死核内置 Slash 解析器 ──> 直接执行（不经模型）
   │
   ├─[显式 'run' / 'model'] ──> 插件路由机制 ──> 校验参数并执行
   │
   └─[自然语言文本] ──> mother-nl 插件 ──> 意图抽取 ──> 映射为标准 Slash / 命令
```

## 3. 安全模型与凭证保护

1. **静态签名校验 (Ed25519)**：
   - 插件载入时，`loader.rs` 读取 `manifest.toml` 并校验签名公钥。
   - 签名失效或未签名的插件目录在运行时被忽略，不注册对应命令。
2. **凭证隔离 (Vault)**：
   - 所有模型 API Key（如 `model.grok.api_key`）存放在受保护的 Vault 存储区。
   - 环境变量与命令行参数中杜绝明文 Token，进程通信走专用 IPC 管道。
3. **503 降级约束**：
   - 单个插件崩溃或被卸载时，对应的功能返回 HTTP/CLI 503 状态，宿主与死核进程保持常驻，不产生级联雪崩。
